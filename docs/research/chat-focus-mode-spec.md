# Спека: режим фокуса в чатах + отдельный канал ответов пользователю

Статус: черновик, 2026-10-25. Выбранные варианты: **C** (явный канал ответа) + **D** (карточки «вопрос → ответ»).

## 1. Проблема

Пользователь пишет лиду запрос («дай отчёт для менеджера»). В лид-чате ответ теряется среди:

- мыслей лида (текст ассистента без `to`), включая нарратив вроде «DEPLOY получил ответ…»;
- переписки лид ↔ тиммейты (`lead → DEPLOY`);
- системных уведомлений (`Potential stalled tasks detected`) и автоматических пинков.

Корень проблемы: сейчас **основной канал ответа лида пользователю — обычный текст**. Промпт прямо это требует
(`src/main/ipc/teams.ts`, stdin для direct message: «Your text response here is shown to the user…»;
`TeamProvisioningInboxRelayPolicy.ts`, `replyVisibility: 'user'`: «a concise plain text reply is allowed»).
В данных ответ неотличим от служебного нарратива, а связи «ответ → запрос» нет.

## 2. Цели и не-цели

Цели:

1. Ответ пользователю — отдельная сущность: сообщение `to: "user"`, сохранённое в `sentMessages.json`/`inboxes/user.json`, со ссылкой на запрос(ы).
2. В каждом чате (общая лента, лид, личка с тиммейтом, групповой) есть тогл **«Фокус»**, который показывает только запросы пользователя и ответы ему.
3. В фокусе видно, на какие запросы ответа нет, и можно одним кликом перейти к ответу.
4. Ничего не пропадает: скрытое сворачивается в раскрываемые полоски.

Не-цели:

- Не меняем обычный (не-фокус) вид таймлайна, кроме мелочей из п. 6.6.
- Не трогаем доставку сообщений тиммейтам и relay-механику.
- Не делаем привязку всех мыслей к ходам (вариант B) — только минимальный учёт хода для подстраховки (п. 5.3).

## 3. Термины

- **Запрос** — сообщение `from: "user"` (`source: user_sent`) в чат.
- **Ответ** — сообщение `to: "user"` от участника команды (лид или тиммейт), кроме служебных видов.
- **Служебное** — всё остальное: мысли лида, лид ↔ тиммейт, `from: system`, `messageKind` ∈
  `task_comment_notification | task_stall_remediation | member_work_sync_nudge | runtime_recovery_nudge`,
  compaction-маркеры, протокольный шум.
- **Фолбэк-ответ** — ответ, который main сам создал из текста лида, когда лид не воспользовался каналом (п. 5.3).

## 4. Контракт данных

Новые необязательные поля `InboxMessage` (`src/shared/types/team.ts`):

```ts
/** Ids of user request messages this reply answers. Stamped by main, never trusted from the model. */
replyToMessageIds?: string[];
/** How the reply to the user was produced. Absent for non-reply messages. */
replyChannel?: 'explicit' | 'fallback';
/** Fallback copy shown only in focus mode; the same text is already visible as a lead thought. */
focusOnly?: boolean;
```

Правила:

- `replyToMessageIds` проставляет только main. Модель его не передаёт и не может подделать.
- Ответы OpenCode-тиммейтов через MCP `message_send` уже несут `relayOfMessageId` при `source: 'runtime_delivery'`.
  Читающая сторона (п. 6.2) трактует его как `replyToMessageIds: [relayOfMessageId]`, если `to === 'user'`.
  Существующее поле не перегружаем новым смыслом при записи.
- Сообщения с `replyChannel: 'fallback'` видны **только в фокусе**. В обычном виде их скрывают:
  исходная мысль лида там и так отображается, дубль не нужен.
- Старые данные без новых полей должны работать: пары строятся по времени (п. 6.2).

## 5. Часть C — канал ответа (main)

### 5.1 Протокол лида

Меняем промпты так, чтобы ответ пользователю всегда шёл через `SendMessage` с `recipient: "user"`,
а обычный текст считался рабочими заметками лида.

Места:

| Где | Сейчас | Станет |
|---|---|---|
| `src/main/ipc/teams.ts`, stdin для direct message лиду | «Your text response here is shown to the user… Always include a brief human-readable reply» | «Answer the user with SendMessage recipient "user". Plain text is your internal working log and is not a reply. One final answer per request; a short acknowledgement first is allowed if the work will take long.» |
| `TeamProvisioningInboxRelayPolicy.ts`, `replyVisibility: 'user'` | «plain text reply is allowed and will be shown to the user» | то же требование, что и выше |
| `TeamProvisioningPromptBuilders.ts`, базовые правила лида | правила оформления сообщений для `"user"` | добавить правило: «Every user request must end with a SendMessage to "user" that answers it. Write that message as a standalone answer: the user may read only that message.» |
| `TeamProvisioningPromptBuilders.ts`, правило про подтверждение после создания задач (строка «your turn ends with a short confirmation to "user"») | уже про `"user"` | без изменений, проверить формулировку |

Ветка `replyVisibility: 'internal_activity'` уже требует `SendMessage → "user"` для уведомлений пользователю — не меняется.

Переключатель для отката: настройка `leadUserReplyChannel: 'explicit' | 'plain_text'`, по умолчанию `explicit`.
Она применяется к новым ходам и не требует перезапуска команды.

### 5.2 Простановка связи (Claude-лид)

Лид-процесс читает stdin. Main знает id каждого запроса, который туда отправил
(`preGeneratedMessageId` в `src/main/ipc/teams.ts`; пачки relay с `replyVisibility: 'user'` несут id inbox-строк).

1. Новый маленький порт состояния хода в рантайме лида: `openUserRequestIds: string[]` и `turnHadUserReply: boolean`.
   Без наследования фасадов и без приведения всего сервиса к host-типу
   (см. `docs/team-management/team-provisioning-target-architecture.md`).
2. Запрос пользователя отправлен в stdin → id добавляется в `openUserRequestIds`.
3. `captureLeadSendMessages` (`TeamProvisioningLeadSendMessageCapture.ts`) поймал `SendMessage → user` →
   в сообщение пишутся `replyToMessageIds = [...openUserRequestIds]` и `replyChannel: 'explicit'`, `turnHadUserReply = true`.
   Если открытых запросов нет (лид пишет по своей инициативе, например «задача готова»), поля не ставятся.
4. Ход закончился (`msg.type === 'result'` в `TeamProvisioningStreamEvents.ts`) → открытые запросы закрываются.
   Если ответа не было, срабатывает фолбэк (п. 5.3).

Склейка: Claude stream-json может обработать несколько сообщений из очереди stdin одним ходом.
Поэтому `replyToMessageIds` — массив: один ответ закрывает все запросы, вошедшие в ход. Это проверяем в фазе 0.

### 5.3 Фолбэк, если лид забыл

Если ход с открытыми запросами закончился без `SendMessage → user`:

- main берёт последний видимый текст лида в этом ходе (без agent-only блоков, без протокольного шума);
- пишет в `sentMessages.json` ответ `from: <lead>, to: 'user'`, `replyChannel: 'fallback'`, `replyToMessageIds`;
- если текста нет, ничего не пишет, и запрос в фокусе остаётся «без ответа»;
- пишет в лог `warn` со счётчиком, чтобы видеть, как часто лид нарушает протокол, и подкручивать промпт.

Когда `leadUserReplyChannel: 'plain_text'`, фолбэк не создаётся.

### 5.4 Другие рантаймы

- Тиммейты Claude/Codex: отвечают нативным `SendMessage → user` и пишут прямо в `inboxes/user.json`. Main это не перехватывает, поэтому связь строится по времени (п. 6.2). Промпт уже требует отвечать в `"user"` (`messageDeliveryText.ts`).
- OpenCode-тиммейты: `message_send` с `relayOfMessageId` даёт точную связь.
- Лид не на Claude (если такой режим поддерживается): проверить в фазе 0. Если лид отвечает через MCP `message_send`, связь даёт `relayOfMessageId`; иначе — по времени.

## 6. Часть D — режим фокуса (renderer)

### 6.1 Где живёт

Новый тонкий слайс `src/features/chat-focus-mode/`:

```
core/domain/
  classifyFocusMessage.ts   // request | reply | service
  buildFocusThread.ts       // пары запрос→ответы + свёрнутые промежутки
renderer/
  storage/chatFocusModeStorage.ts   // localStorage, по образцу pinnedChatsStorage
  hooks/useChatFocusMode.ts
  ui/FocusModeToggle.tsx
  ui/FocusThreadView.tsx
  ui/FocusRequestCard.tsx
  ui/FocusServiceStrip.tsx
  index.ts
```

Зависит от `@features/team-direct-chats` (`ConversationScope`, `conversationScopeKey`, `belongsToConversation`).
Main не трогает: всё из раздела 5 — это изменения в provisioning, а не в этом слайсе.

### 6.2 Логика (чистые функции)

`classifyFocusMessage(message, scope, leadNames)`:

- `request`: `from === 'user'`, не slash-команда.
- `reply`: `to === 'user'`, `from` — участник этого чата (в лид-чате — алиасы лида; в ленте — любой),
  `messageKind` не служебный, не протокольный шум (`isInboxNoiseMessage`, `isTeamInternalControlMessageEnvelope`).
- `service`: всё остальное. Мысли лида всегда здесь.

`buildFocusThread(messages)` → список элементов:

```ts
type FocusItem =
  | { kind: 'pair'; request: InboxMessage; replies: InboxMessage[]; status: 'answered' | 'pending' }
  | { kind: 'unsolicited-reply'; reply: InboxMessage }          // ответ без запроса, например отчёт о задаче
  | { kind: 'service-gap'; messages: InboxMessage[] };          // свёрнутая полоска
```

Привязка ответа к запросу, по приоритету:

1. `replyToMessageIds` (или `relayOfMessageId` для `runtime_delivery`);
2. по времени: последний запрос в этом чате с меньшим timestamp к тому же собеседнику
   (в ленте — с учётом `to` запроса). Это покрывает тиммейтов и старую историю.

Статус `answered`: есть хотя бы один ответ с `replyChannel !== undefined` или привязанный по времени.
Ответы, пришедшие после следующего запроса, но явно ссылающиеся на ранний, остаются у раннего (сценарий «принял» → позже итог).

### 6.3 Тогл

- Кнопка «Фокус» (иконка `Focus` / `Target` из lucide) в `ConversationHeader` через проп `actions`, во всех видах чата.
- Состояние хранится отдельно для каждого чата: ключ `team-chat-focus:<teamName>`, значение — набор `conversationScopeKey`.
  Хранилище — маленький репозиторий, UI не трогает `localStorage` напрямую.
- Горячая клавиша `Alt+F`, когда открыт чат.
- По умолчанию выключен. Глобальная настройка «включать фокус по умолчанию» — фаза 2.

### 6.4 Вид в фокусе

- **Карточка запроса**: твоё сообщение, под ним ответ(ы) полностью, без «Show more».
  Фолбэк-ответ помечен тегом «ответ из рабочего лога» приглушённым цветом.
- **Статус** на карточке без ответа: «ждёт ответа» и состояние собеседника (работает / офлайн), из уже существующего lead activity.
- **Полоска «N служебных событий»** между карточками: по клику раскрывает скрытые сообщения этого промежутка обычным рендером таймлайна.
- **Счётчик в шапке**: «2 без ответа», по клику прокручивает к самому раннему.
- В обычном виде у каждого твоего сообщения появляется маленькая ссылка «↳ ответ», если ответ найден: переход и подсветка.
- Композер работает как обычно; новое отправленное сообщение сразу появляется как карточка «ждёт ответа».

### 6.5 Что скрывается по видам чатов

| Чат | Запросы | Ответы | Скрыто |
|---|---|---|---|
| Лид | user → лид | лид → user | мысли, лид ↔ тиммейты, system, пинки |
| Личка с тиммейтом | user → X | X → user | бутстрап лида для X, пинки, уведомления о комментариях |
| Общая лента | все user → * | все * → user | всё прочее |
| Групповой | сообщения user | сообщения участников | system, автоматика; пары по времени (до следующего сообщения user) |

### 6.6 Мелочи в обычном виде

- Скрыть сообщения `replyChannel: 'fallback'` (дубль мысли).
- Ссылка «↳ ответ» у запросов (п. 6.4).

## 7. Фазы работ

0. **Разведка (полдня).** Проверить склейку stdin в один ход у Claude stream-json; проверить, какие рантаймы бывают лидом и чем они отвечают пользователю; проверить, что `sentMessages.json` переживает перезапуск команды и попадает в лид-чат через `belongsToConversation`.
1. **Контракт.** Поля `replyToMessageIds`, `replyChannel` в `InboxMessage`, сохранение и чтение в inbox/sent-хранилищах, валидация IPC. Тесты сериализации.
2. **Протокол (C).** Тексты промптов из п. 5.1, настройка `leadUserReplyChannel`. Тесты на тексты промптов.
3. **Простановка и фолбэк (C).** Порт состояния хода, правки `captureLeadSendMessages`, обработчик `result`. Юнит-тесты: один запрос; склейка двух; ответ без запроса; ход без ответа → фолбэк; ход без ответа и без текста.
4. **Домен фокуса (D).** `classifyFocusMessage`, `buildFocusThread` с тестами на все строки таблицы 6.5 и на историю без новых полей.
5. **UI (D).** Тогл, хранилище, карточки, полоски, счётчик, `Alt+F`, ссылка «↳ ответ». Локализация ru/en.
6. **Проверка.** `pnpm typecheck`, `pnpm test`, `pnpm guard:source-file-size`, `pnpm guard:team-provisioning-architecture`; живой прогон команды: запрос лиду → ответ в фокусе, ответ привязан, служебное свернуто.

## 8. Критерии приёмки

1. В лид-чате со скриншота (запрос «дай отчёт», затем 10+ служебных событий) фокус показывает одну карточку: запрос и ответ лида.
2. Если лид ответил текстом без `SendMessage`, карточка всё равно показывает ответ с пометкой фолбэка, в логе есть предупреждение.
3. Запрос без ответа виден как «ждёт ответа» и считается в счётчике шапки.
4. Состояние тогла сохраняется для каждого чата отдельно и переживает перезапуск приложения.
5. Раскрытие полоски показывает ровно те сообщения, которые были скрыты в этом промежутке.
6. Старая история без новых полей показывает пары по времени без ошибок.
7. Обычный вид не изменился, кроме п. 6.6.

## 9. Риски и открытые вопросы

- **Дисциплина модели.** Лид может продолжать отвечать текстом. Закрывается фолбэком и счётчиком в логе; если доля фолбэков высокая — усиливать промпт.
- **Двойные ответы.** Лид может ответить и текстом, и `SendMessage`. В обычном виде пользователь увидит оба, как и сейчас; фолбэк при этом не создаётся.
- **Склейка ходов.** Если подтвердится, что ход может смешать запрос пользователя и relay от тиммейта, ответ всё равно привяжется к запросу — это нужное поведение.
- **Тиммейты без точной связи.** Пара по времени может ошибиться, если пользователь шлёт тиммейту несколько запросов подряд. Для v1 приемлемо.
- **Вопрос:** включать ли фокус по умолчанию в лид-чате? Предложение: нет в v1, глобальная настройка в фазе 2.

## 10. Результаты фазы 0 (разведка, 2026-10-25)

1. **Два пути запроса к лиду.**
   - Прямой: лид жив и не OpenCode → `src/main/ipc/teams.ts` сразу пишет в stdin (`sendMessageToTeam`) с `preGeneratedMessageId`.
     Ответ лида текстом нигде не превращается в сообщение `to: user` — он виден только как мысль.
   - Через inbox: лид офлайн или занят relay → `TeamProvisioningLeadInboxRelayFlow.ts`. Для пачек от пользователя
     (`replyVisibility: 'user'`) уже есть захват текста хода (`run.leadRelayCapture`) и проекция
     `projectLeadRelayReply` → `to: user` в `sentMessages.json`. Если в ходе был `SendMessage → user`, текст подавляется
     как дубль. То есть **фолбэк для relay-пути уже существует**; нужно только проставить `replyToMessageIds` (id пачки)
     и `replyChannel: 'fallback'`. В обычном виде эти сообщения остаются видимыми, как сейчас.
2. **Рантаймы лида.** Все не-OpenCode лиды (Anthropic, Codex и др. провайдеры) — это один stream-json процесс:
   stdin-пейлоад собирается с `providerId`, а `SendMessage` перехватывается из stdout в `captureLeadSendMessages`.
   OpenCode-лид получает сообщения через runtime delivery, где связь даёт `relayOfMessageId`.
3. **Склейка ходов.** Режим `--replay-user-messages` не используется, поэтому main не видит, когда CLI забрал сообщение
   из stdin. Прямой путь пишет в stdin даже во время чужого хода, и CLI может обработать сообщение позже или подмешать в
   текущий ход. Поэтому для прямого пути правило такое:
   - запрос открыт с момента записи в stdin;
   - `SendMessage → user` закрывает все открытые запросы и получает их id;
   - `result` закрывает запрос фолбэком, только если ход начался после отправки запроса
     (лид был свободен при отправке или после отправки уже был хотя бы один `result`);
     в фолбэк идёт текст лида, полученный после начала этого хода.
4. **Фолбэк прямого пути** пишется в `sentMessages.json` с `replyChannel: 'fallback'` и `focusOnly: true`:
   в обычном виде он скрыт, потому что тот же текст уже показан мыслью лида.
5. **Хранилища с белыми списками полей**, куда надо добавить новые поля: `TeamSentMessagesStore`, `TeamInboxReader`,
   `TeamDataWorkerClient`, `TeamProvisioningMessagePersistence`, `teamMessagesCache` (сравнение), `messageRenderEquality`.
6. **Ограничения размера.** `src/main/ipc/teams.ts` заморожен с запасом 10 строк — туда только правки текста промпта и
   передача id запроса. Логику хода держим в новом модуле provisioning.

## 11. Итоги реализации (фазы 1–6, 2026-10-25)

Сделано:

- **Контракт.** `UserReplyLinkFields` (`replyToMessageIds`, `replyChannel`, `focusOnly`) в `src/shared/types/userReplyLink.ts`,
  `InboxMessage` их наследует. Чтение и проверка — `readUserReplyLinkFields`; связь ответа с запросом, включая
  OpenCode `relayOfMessageId`, — `getUserReplyRequestIds` (`src/shared/utils/userReplyLink.ts`).
- **Протокол лида.** Тексты в `src/main/services/team/leadUserReplyChannel.ts`; правило канала ответа добавлено в
  `buildActionModeProtocol` (файл `PromptBuilders` заморожен).
- **Простановка и фолбэк.** `TeamProvisioningLeadUserReplyTracker.ts`: открытые запросы, счёт ходов по `result`,
  связь для `SendMessage → user`, фолбэк прямого пути. Relay-путь проставляет связь в `projectLeadRelayReply`.
- **Домен фокуса.** `src/features/chat-focus-mode/core/domain`: `classifyFocusMessage`, `buildFocusThread`,
  `summarizeFocusThread`, `buildFocusReplyIndex`.
- **UI.** Тогл с иконкой `Focus` в шапке любого открытого чата, счётчик «Без ответа: N» с прокруткой к самому раннему,
  `Alt+F` (срабатывает только у видимого тогла), карточки запрос → ответы, пометка фолбэка, «ждёт ответа»,
  сворачиваемые полоски служебных событий. Хранилище — `team-chat-focus:<teamName>`. Строки — во всех 29 локалях.
- **Обычный вид.** Сообщения `focusOnly` скрыты из таймлайна и не считаются непрочитанными.

Отклонения от спеки:

- **Откат канала ответа — только переменная окружения** `AGENT_TEAMS_LEAD_USER_REPLY_CHANNEL=plain_text`, без настройки в UI.
- **Ссылка «↳ ответ» в обычном виде не сделана.** Индекс для неё готов (`buildFocusReplyIndex`), но рендер сообщения
  (`ActivityItem.tsx`) заморожен по размеру; нужен отдельный небольшой рефакторинг.
- **Статус собеседника** (работает / офлайн) на карточке «ждёт ответа» не выводится.
- **Раскрытая полоска** показывает сообщения обычной карточкой `ActivityItem`, а не группировкой таймлайна
  (мысли лида не склеиваются в одну группу).
- **Уведомления.** Фолбэк-ответ пишется в `sentMessages.json` с `read: true`; возможное системное уведомление о нём
  не проверялось вживую.

Не проверено: живой прогон команды (критерии приёмки 1–3) — нужен запуск приложения с лидом.

Правки после живой проверки (лид-чат `tokenplan-ops`, 2026-10-25):

- **Автодогрузка истории.** В загруженной голове занятой команды нет ни одного запроса, поэтому режим фокуса сам
  догружает старые страницы, пока не появится запрос (`useFocusAutoOlder`). Страницы грузятся по одной.
  Страница засчитывается, если загрузка прошла, даже когда в ней нет сообщений этого чата.
  Загрузку, которую стор пропустил (не поднял `loadingOlder` за 2 с), хук повторяет.
  Лимиты: 10 страниц и 5 пропусков подряд. Пока поиск идёт, вместо «Запросов нет» показано «Ищу ваши запросы…».
- **Счётчик в шапке.** Вместо текста «Без ответа: N» — компактный значок с часами и числом, полный текст в подсказке и
  `aria-label`; больше не наезжает на «Full Screen».
- **Дубль ответа лида.** `SendMessage → user` лида хранится дважды: в `inboxes/user.json` и как захваченное
  сообщение в `sentMessages.json` (со связью). `buildFocusThread` оставляет одну копию — одинаковый автор и текст
  в пределах 10 с, предпочитая копию со связью.

Правки после ревью (2026-10-25):

- **Ответ после подтверждения.** Явный ответ лида связывается только с запросами, которые текущий ход уже получил. Запрос, пришедший, пока лид был занят, ждёт своего хода. Ответ без нового запроса (результат после «Принял») наследует ids последнего отвеченного запроса и попадает в ту же карточку.
- **Дубли.** Одинаковые ответы склеиваются, только если у них совпадают ссылки на запросы или ссылки есть лишь у одной копии. Сообщения классифицируются один раз за сборку.
- **Автодогрузка.** Страница считается по флагу загрузки стора, а не по росту истории: живые сообщения в голове не засчитываются как страницы. Состояние поиска привязано к ключу чата и сбрасывается при переходе между группами.

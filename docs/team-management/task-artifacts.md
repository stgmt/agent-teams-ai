# Required task artifacts

In a task's Attachments section, enable **Require a task artifact**. You can set a required filename before the file exists, then choose the file to attach. If no filename is set, any filename is accepted. The app calculates its size and SHA-256 and stores a copy under `<claudeDir>/teams/<team>/task-attachments/<taskId>` (this is separate from the appData attachment directory). The attached copy can be downloaded from the task. The file limit is 20 MiB. To refer to a larger video, you can attach a small manifest with its location and expected hash; the app verifies only that manifest, not the referenced video.

An agent can attach the requested filename with MCP `task_set_artifact_file` using `teamName`, `taskId`, `actor`, `filename`, and `base64Data`. Base64 expands the payload and may consume substantial MCP context, so this is unsuitable for large files. If no filename was specified, the first attached filename becomes the expected name. An agent cannot change a specified filename. Before completion, another attachment with that same name replaces the stored copy and its proof; it does not retain a version history. The MCP `actor` is caller-provided and checked against the configured owner under the existing MCP model; it does not authenticate the process's identity.

Completion and transitions into review or approval re-read the stored copy and reject a missing, unreadable, or changed artifact. Reopen a completed or approved task before enabling a new requirement, changing its filename, or attaching another copy. Existing tasks have no artifact requirement by default; the user can disable one. Hashing is synchronous and bounded to 20 MiB, so slow storage may still temporarily block the app or MCP server.

The server never reads an agent-provided project path when attaching an artifact. The team task-attachments directory is trusted storage; it is not isolated from an agent or another local process with write access under the same OS account. SHA-256 and size identify the bytes that were read, not their quality. Download verifies the returned bytes, but a separate check does not make later use of the file atomic; consumers must verify again immediately before using it.

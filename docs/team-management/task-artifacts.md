# Required task artifacts

In a task's Attachments section, enable **Require a task artifact**. You can set a required filename before the file exists, then choose the file to attach. If no filename is set, any filename is accepted. For a registry-backed task, the desktop app stores the copy under its data directory in `task-attachments/<team>/<taskId>` and records its size and SHA-256. An unlinked team's local task uses `<claudeDir>/teams/<team>/task-attachments/<taskId>`. The attached copy can be downloaded from the task. The file limit is 20 MiB. To refer to a larger video, you can attach a small manifest with its location and expected hash; the app verifies only that manifest, not the referenced video.

An agent can attach the requested filename with MCP `task_set_artifact_file` using `teamName`, `taskId`, `actor`, `filename`, and `base64Data`. Base64 expands the payload and may consume substantial MCP context, so this is unsuitable for large files. If no filename was specified, the first attached filename becomes the expected name. An agent cannot change a specified filename. Before completion, another attachment with that same name replaces the stored copy and its proof; it does not retain a version history. The MCP `actor` is caller-provided and checked against the configured owner under the existing MCP model; it does not authenticate the process's identity.

Completion and transitions into review or approval re-read the stored copy and reject a missing, unreadable, or changed artifact. Reopen a completed or approved task before enabling a new requirement, changing its filename, or attaching another copy. Existing tasks have no artifact requirement by default; the user can disable one. Hashing is synchronous and bounded to 20 MiB, so slow storage may still temporarily block the app or MCP server.

For a registry-backed task, the app checks the local copy and signs the server-issued confirmation before requesting completion. The registry receives the file's digest, size and signature, not its bytes or local path. Controller writes send file bytes only to the app-bound local control API; downloads address team, task and attachment IDs, verify the returned bytes against task proof metadata, and never expose a local path. If the outcome of a submitted confirmation is unknown, the app must recover the original request rather than assume success or submit a different confirmation.

Artifact editing and download are available in the local Electron app; browser/standalone and remote contexts show the controls as unavailable. Before sending an update, the app stores an operation marker for the task and its physical data-root fingerprint in the renderer profile's IndexedDB. The main process derives that fingerprint from the directory's operating-system device and file identifiers, and checks it again under the expected connection context before a write. A filesystem must provide stable, nonzero identifiers; if they are unavailable, editing is disabled. A second guarded UI operation in that profile cannot start until the first has a confirmed result or the user explicitly resolves an unknown result. This guard survives renderer restarts, but does not serialize other profiles, MCP agents, or other processes. If its storage is unavailable, the app does not send the update. Switching the data root waits for an admitted write and rejects a stale request.
If a UI update loses its response, remains pending for 30 seconds, or the following refresh cannot be confirmed, the app marks its result as unknown and does not repeat or cancel the write. It lets you read the current task and then asks whether to allow new changes. The read is a snapshot; a delayed earlier request could still finish later. A recovered marker keeps its operation type and attempt identifier, so a different operation cannot clear it. Explicit decisions are retained in the profile's IndexedDB without automatic expiry, including when a new attempt starts, so a late response can see that the user already decided. These receipts can grow over time; clearing the profile's storage removes them.

The server never reads an agent-provided project path when attaching an artifact. Artifact changes are submitted separately from ordinary task fields, avoiding asynchronous group-chat validation between root admission and the controller call. Root checking is not a pinned filesystem handle: another process that can replace filesystem components can still race the check and write. The team task-attachments directory is trusted storage; it is not isolated from an agent or another local process with write access under the same OS account. SHA-256 and size identify the bytes that were read, not their quality. Download verifies the returned bytes, but a separate check does not make later use of the file atomic; consumers must verify again immediately before using it.

## Board coordination limits

Current-version controller and desktop board operations acquire a lock in the physical Claude root and then the existing team-directory lock. This keeps current-version operations separated if a team directory or the `teams` directory is moved while an operation is active, including when the same Claude root is reached through a junction or symlink. It does not protect an arbitrary move or replacement of the Claude root itself.

Launch-state publication and backup restore also share a separate cross-process lock at the physical Claude root. It keeps a stop from replacing a new launch that is published concurrently; operations wait for the lock or report failure, and do not repeat a publication whose outcome is unknown.

Older desktop versions and older controller/MCP processes do not use the shared board or launch-publication locks. Running older and newer versions against the same team data at the same time is unsupported: close every older app instance and controller/MCP process before launching the new version. A concurrent older writer can still replace a board update, even when a snapshot was checked immediately before publication. This mixed-version race remains unresolved; the current snapshot check only detects changes that occur before that check.

If stopping a team encounters an unresolved review transition whose activity interval needs to change, the original stop finishes its process teardown and the app reports that the timer was not finalized. Another process may already have launched a new run. The transition, its hash and its history are preserved for the explicit review-recovery flow; no uncertain write is repeated automatically. The app does not yet offer a fenced action to finish that timer after recovery while another process might launch the team. Inspect the current run, task and timer rather than assuming the stop finalized its activity record.

Recovery decisions for one transition are coordinated between windows of the same Electron or browser profile using IndexedDB. The decision is recorded before a recovery write is sent; an uncertain response does not cause another confirmation or automatic write. A successful response is recorded separately. These records have no automatic expiry and can accumulate; clearing profile storage removes them. Other profiles are not coordinated. If IndexedDB is unavailable, recovery remains blocked for manual inspection. Recovery does not automatically repeat the original action or its follow-up notifications.

After an application restart, a remaining run may no longer have a locally verifiable owner. In that case, force-cleanup does not remove processes, queues or launch state whose ownership cannot be established, and reports an incomplete result. Inspect the current run and its processes manually; there is not yet a dedicated fenced action to clean up such an orphan.

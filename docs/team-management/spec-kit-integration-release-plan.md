# План релиза: полноценная интеграция Teams со Spec Kit

Статус: запланирован, реализация и выпуск не выполнены. Это отдельный новый релиз приложения; номер версии и тег назначаются по фактическому состоянию релизной ветки, без изменения существующих тегов.

## Результат релиза

Лид и участники команды используют существующие MCP-инструменты Spec Kit: создают спецификации, проходят требования → проектирование → критерии приёмки, создают и выполняют задачи, отправляют отчёт и закрывают работу. Поддерживаются жизненный цикл спецификации и дорожная карта. Результат доступен в Teams, сохраняется после перезапуска и не открывает доступ к чужим проектам.

Не входят: переписывание всего управления командами, второй MCP-сервер, собственные инструменты управления спецификациями, параллельное хранилище задач, глобальное подключение пользовательского токена агентам.

## Исходные факты и рабочая база

Проверено в `E:/tmp/agts-release-latest-20261109`: переходник `mcp-server/src/tools/specProxyTools.ts` уже получает инструменты и схемы из реестра. В `NodeTeamLaunchSettings.ts` первоначальная привязка учитывается в брифинге, но параметры доступа и область команды всё ещё зависят от другого представления привязки. `mcp-server/src/index.ts` допускает запуск после ошибки регистрации инструментов.

Это факты исходного кода, не подтверждение содержимого установленного приложения. Перед реализацией собрать необходимые существующие изменения в одной изолированной релизной ветке, сохранив постороннюю работу; сборку и приёмку выполнять только из неё.

## Архитектурный контракт: SOLID, DRY, KISS, ООП

- **Одна ответственность (S):** `NodeTeamLaunchSettings` определяет проверенную конфигурацию; `NodeNativeLaunchArtifacts` и `TeamMcpConfigBuilder` подготавливают запуск; `specProxyTools` связывает MCP с реестром; `specGateway` ограничивает область команды; реестр владеет операциями и состоянием.
- **Расширяемость (O):** новые инструменты и схемы поступают из реестра без ручного изменения каталога приложения. Не копировать схемы и бизнес-логику операций.
- **Единые гарантии (L):** первоначальный запуск, повторный запуск и восстановление соблюдают один контракт интеграции; ни один путь не допускает успешный запуск без необходимых инструментов.
- **Узкие интерфейсы (I):** использовать существующие целевые порты; не передавать целые сервисы и не скрывать несовместимость приведениями типов.
- **Зависимость от контрактов (D):** запуск получает подключение из приложения, а не ищет самостоятельно токен, файл или другой сервер. Учётные данные принадлежат приложению и передаются только MCP-процессу, не модели и её оболочке.
- **Инварианты объектов (ООП):** одна проверенная конфигурация содержит разрешённый проект, список связанных спецификаций и параметры MCP. Состояние «инструкция есть, подключения нет» недопустимо. Пустой список спецификаций допустим для создания первой, отсутствие разрешённого проекта — нет. Использовать композицию, без новой иерархии фасадов.
- **Один источник правила (DRY):** одна внутренняя модель привязки, одна проверка области доступа, один источник схем и одно хранилище задач/спецификаций.
- **Минимальная конструкция (KISS):** доработать существующий путь. Не добавлять менеджер интеграций, новый транспорт, отдельный BDD-раннер, дублирующие API и промежуточные хранилища.

## Порядок реализации: сначала поведение, затем код

Для каждого изменяемого поведения соблюдать TDD: **падающий тест с ожидаемой причиной → минимальное исправление → рефакторинг → повторная проверка затронутого поведения**. Падение окружения или неопределённый шаг не считать доказательством дефекта.

1. **Настройка новым пользователем.** Через стандартный интерфейс приложения настроить подключение к Spec Kit и разрешённый проект команды. Приложение получает и сохраняет персональные учётные данные, загружает их при следующем запуске и предлагает настройку, если подключение не готово. Ручная подготовка переменных окружения или файла токена не является условием работы нового пользователя. Секреты не попадают в брифинг, журналы и окружение модели.
2. **Единая привязка.** Преобразовывать данные формы на входной границе в одну внутреннюю модель; использовать её для инструкций, области доступа и подключения. Старые сохранённые команды переводить однократной миграцией до запуска. Затем удалить чтение старых полей из рабочего пути. При ошибке миграции — явный отказ, без альтернативного чтения старого формата.
3. **Согласованный запуск.** В существующих типах и интерфейсах исключить независимые необязательные параметры, позволяющие запуск с половиной конфигурации. Обновить всех потребителей, включая восстановление; не оставлять совместимые псевдонимы и запасные ветки.
4. **Обязательная готовность полного MCP.** Удалить молчаливый пропуск регистрации и продолжение после `registration skipped`. С первого запуска лид и участники получают полный опубликованный набор инструментов Spec Kit, включая запись, без начального read-only-поднабора и ручной копии каталога. Сопоставлять доступные инструменты с текущими дескрипторами реестра, а не с закреплённым числом названий. Неполная конфигурация, отказ авторизации и ошибка обнаружения инструментов завершают запуск понятной ошибкой в Teams. Вся логика ожидания и восстановления подключения остаётся на стороне Spec Kit; Teams получает результат и не вводит собственное ожидание или цикл опроса реестра.
5. **Тонкий переходник и единственный путь изменения задач.** Сохранить опубликованные реестром схемы, проверку разрешённого проекта и передачу отказов. Создание задачи, назначение, изменение статуса, результат и ревью проходят через существующий общий MCP-адаптер и поддерживаемый контракт реестра. Удалить прежние внутренние пути записи приложения и обновить всех их потребителей, а не оставить их запасным маршрутом. Отчёт исполнителя доходит до лида сообщением. Удалить подтверждённо мёртвые ветки и устаревшие подсказки; не заменять ошибки пустым успешным результатом.
6. **Работа агента.** Переписать брифинг под фактически зарегистрированные инструменты и рабочий процесс, без копирования JSON-контрактов. Сохранить существующий хук запрета прямой записи спецификаций и задач. Создание спецификации должно автоматически связывать её с командой через контракт реестра; не добавлять отдельный маршрут привязки. Проверить этот контракт, а недостающую возможность реализовать в существующей операции реестра, не в обходном пути приложения.
7. **Восстановление после аварии.** Проверить принудительное завершение приложения во время незаконченной работы, а не только штатный выход. После запуска восстановить привязки и незавершённую работу без повторного создания спецификаций, задач и назначения исполнителей. Если агентские процессы пережили остановку приложения, они должны снова отображаться в списке процессов Teams.
8. **Чтение доски и ожидание агента.** Сохранить быстрый путь чтения через существующий адаптер. Перед изменениями зафиксировать время чтения доски и действующий бюджет агентского запроса; сравнить результат после изменений в одинаковых условиях. Чтение должно укладываться в этот бюджет без регрессии относительно базы; агент не должен преждевременно обрывать допустимое ожидание и повторять тот же запрос по кругу. Увеличение таймаута само по себе не считается исправлением.

## Исполняемая приёмка поведения — BDD

Сценарии реализовать существующими средствами проекта через наблюдаемую границу. Добавлять только недостающие поведенческие проверки; тесты на формулировки, наличие названий и копирование аргументов удалить, а не перепривязать к новому тексту.

| Дано / когда | Обязательный результат |
| --- | --- |
| Новый пользователь ещё не настраивал интеграцию | Приложение предлагает настройку вместо запуска команды без Spec Kit; пользователь завершает подключение через интерфейс без ручной подготовки окружения |
| Пользователь настроил подключение и перезапустил приложение | Учётные данные и разрешённый проект сохранены; повторный ручной ввод токена не нужен |
| Новая команда получила разрешённый проект через интерфейс | С первой сессии у лида и участников доступен полный опубликованный набор чтения и записи; каждым участником выполнены реальные разрешённые вызовы, а не только получен брифинг |
| У команды ещё нет спецификаций; лид создаёт первую | Спецификация читается и перечисляется инструментами реестра, автоматически связана с создавшей командой и доступна в Teams |
| Агент меняет статус созданной спецификации | Разрешённый контрактом переход действительно сохранён в реестре; последующее чтение и приложение показывают новое состояние |
| Агент захватывает свободную спецификацию | Реестр подтверждает захват этим агентом и разрешает предусмотренную контрактом запись |
| Другой агент пытается захватить уже занятую спецификацию | Получен явный отказ; существующий захват и данные первого агента не изменены |
| Владелец освобождает спецификацию | Захват снят в реестре; другой агент может затем успешно захватить спецификацию |
| Реестр недоступен, отклонил учётные данные или регистрация не состоялась | Команда не показана готовой; причина отказа доступна в приложении |
| Реестр отклонил запись после успешного запуска команды | Агент и приложение получают отказ; задача не закрывается, успешный результат не выдумывается, обходной путь записи не включается |
| Агент запрашивает чужой проект | Отказ без чтения и изменения чужих данных; создание новой спецификации не расширяет разрешённую область команды |
| Команда проходит требования, проектирование и критерии приёмки | Сохранены содержательные документы, проверка спецификации проходит; не принимается формальный текст-заполнитель |
| Лид создал задачу и назначил исполнителя | Исполнитель читает спецификацию, выполняет работу и отправляет лиду отчёт; изменения задачи проходят через общий MCP-адаптер, задача закрывается и видна в Teams |
| Приложение штатно остановлено и запущено повторно | Привязка и работа сохранены; задачи и спецификации не создаются повторно |
| Приложение принудительно завершено во время работы и запущено повторно | Незавершённая работа восстанавливается без повторного создания объектов; оставшиеся живыми агенты отображаются в списке процессов |
| Лид и исполнитель читают доску во время рабочего цикла | Чтение укладывается в заранее зафиксированный бюджет без регрессии; агент не запускает цикл преждевременной отмены и повторного чтения |
| Агент создаёт дорожную карту и связывает её со спецификациями | Документ и связи сохранены реестром, проходят проверку и доступны через приложение |

## Проверки, сборка и выпуск

1. Во время TDD запускать минимальный затронутый набор: тесты настройки и сохранения интеграции, настроек запуска, подготовки MCP, регистрации инструментов, шлюза области доступа, операций задач и восстановления в существующих пакетах. Для каждого сценария приёмки указать покрывающую проверку; незакрытый сценарий блокирует выпуск. Не создавать проверки текста вместо проверок поведения.
2. Перед выпуском выполнить `pnpm check` по [правилам проекта](../GIT_DELIVERY_POLICY.md); не обходить ревью, обязательный CI и архитектурные ограничения.
3. Живая приёмка: `pnpm dev:mcp`, доказанное происхождение сборки из релизной ветки, реальный провайдер с доступной в Claude Code моделью DeepSeek Flash и небольшая команда — лид плюс два исполнителя. Пройти сценарии выше и сохранить отдельный результат каждого, включая настройку новым пользователем, первоначальный запуск, повторный запуск, аварийное восстановление и измерение чтения доски. Нужны результаты реальных вызовов и доказательства в интерфейсе Teams. Заглушки, прямой запрос оператора к реестру, текст брифинга и список инструментов сами по себе не заменяют эту приёмку.
4. Если изменён контракт реестра, сначала выпустить и проверить совместимый реестр, затем приложение. Несовместимый реестр — блокировка выпуска, не повод включить обходной путь.
5. Обновить существующую документацию и пользовательские заметки релиза. Зафиксировать проверенный коммит, назначить новую версию/тег, собрать установщики по [Release Guide](../RELEASE.md). Проверить запуск упакованного приложения и обновление предыдущей установки с сохранением данных; живое подтверждение не должно относиться только к dev-сборке.
6. Опубликовать через установленный процесс выпуска; сверить коммит тега, скачиваемые установщики и метаданные обновления. При провале обязательной проверки релиз не публиковать и не объявлять готовым. Аварийное возвращение предыдущего выпуска — операторская процедура с сохранением данных, не встроенный запасной путь выполнения.

## Условия завершения

Релиз завершён только после живой полной цепочки в Teams и проверки опубликованного пакета. Каждый сценарий приёмки подтверждён отдельно. Новый пользователь настраивает интеграцию через интерфейс; лид и участники получают полный набор инструментов с первого запуска; аварийный перезапуск сохраняет работу и видимость живых процессов; чтение доски не замедлено и не вызывает повторных обрывов ожидания. Старые форматы в рабочем пути и прежние внутренние записи задач удалены; прямые файловые записи запрещены; учётные данные не доступны модели; чужие проекты недоступны. Никаких скрытых частичных успехов, альтернативных серверов/токенов, локальных замен реестра и совместимых обходов.
